# tools/

Служебные скрипты проекта. По ТЗ (раздел «Порядок работы», этап Git) в
репозиторий попадают custom/child theme, MU-plugins, `tools` и `docs`.

## qa/ — проверка без браузера

Стенд закрыт HTTP Basic Auth на уровне Caddy, учётных данных у разработчика
нет, а участок Caddy → Beget периодически теряет параллельные соединения, из-за
чего браузерная проверка нестабильна. Поэтому серверная половина QA вынесена в
скрипты: они поднимают WordPress прямо в PHP и разбирают полученную разметку.

**Runtime сайта — PHP 8.2**, системный `php` в консоли другой версии, поэтому
путь к интерпретатору указывается явно.

```bash
# все ключевые страницы разом: 404, редиректы, замечания PHP, битые ассеты
/usr/local/php/cgi/8.2/bin/php tools/qa/smoke.php

# то же, но HTML-дампы страниц остаются в tools/qa/out/ для ручного разбора
/usr/local/php/cgi/8.2/bin/php tools/qa/smoke.php --keep

# + проверить каждую внутреннюю ссылку со всех этих страниц (около минуты)
/usr/local/php/cgi/8.2/bin/php tools/qa/smoke.php --links

# одна страница в stdout (состояние — в stderr)
/usr/local/php/cgi/8.2/bin/php tools/qa/render.php /remeshki-whoop-mg/ > page.html
```

```bash
# чего не хватает в карточках товаров, чтобы запрос к заказчику был точным
/usr/local/php/cgi/8.2/bin/php tools/qa/products.php
/usr/local/php/cgi/8.2/bin/php tools/qa/products.php --list
```

Код возврата: `0` — замечаний нет, `1` — есть (`products.php` считает
замечанием только товар без цены: его нельзя купить).

### Что эти скрипты проверяют

* страница открывается и не отдаёт неожиданный 404;
* нет неожиданного редиректа (ожидаемые перечислены в самом скрипте:
  архивы категорий → страницы каталога, пустое оформление заказа → корзина);
* PHP не пишет warning / notice / deprecated (на стенде `WP_DEBUG` выключен,
  поэтому скрипт ставит собственный обработчик ошибок);
* все локальные картинки, стили, скрипты и шрифты, на которые ссылается
  разметка, действительно лежат на диске — пункт ТЗ «нет broken assets»;
* с флагом `--links` — что ни одна внутренняя ссылка не ведёт на 404.

Известное замечание, которое `--links` показывает намеренно: ссылка
«Политика конфиденциальности» в подвале ведёт на 404, потому что страница —
черновик с заготовкой WordPress. Нужен текст от заказчика; выдумывать
юридический текст нельзя.

### Чего они НЕ проверяют

Ошибки консоли браузера, внешний вид, поведение скриптов, диапазон
320–1440 px и доступность стенда снаружи. Это только браузером.

### products.php

Показывает, у скольких товаров не заполнены цена, фото, описание, артикул, вес
и габариты, и что из этого чем грозит. Товары заводились из данных макета,
поэтому часть полей заполнить было нечем — выдумывать цены, описания и
артикулы нельзя, и скрипт превращает это в точный список к заказчику.

### shipping.php

Выбор способа доставки и ПВЗ через Store API — те же маршруты, что вызывает
форма «Ваш заказ», только внутри процесса PHP. Тарифы СДЭК считает настоящий
плагин в тестовом режиме, поэтому нужен интернет; прогон — около двух минут.

```bash
/usr/local/php/cgi/8.2/bin/php tools/qa/shipping.php
```

Проверяет: выбранный способ не подменяется другим, когда пропадает (город
неизвестен СДЭК, ошибка API), и оформление без способа отклоняется;
«Экспресс» и «Самовывоз» переживают смену города; код ПВЗ сверяется со списком
пунктов города и с типом пункта. В базе ничего не остаётся — прогон идёт в
транзакции с откатом, но номера заказов расходуются.

### yookassa.php и telegram.php

Код проекта вокруг ЮKassa и уведомления в Telegram — без ключей и без
настоящего бота. Сеть наружу закрыта, Telegram подменён на уровне HTTP,
заказы и настройки — в транзакции с откатом.

```bash
/usr/local/php/cgi/8.2/bin/php tools/qa/yookassa.php
/usr/local/php/cgi/8.2/bin/php tools/qa/telegram.php
```

`yookassa.php`: на staging ЮKassa предлагается только с тестовым ключом;
возврат после оплаты ведёт на Главную с модалкой только при совпавшем ключе
заказа. `telegram.php`: при «Тестовой оплате» уведомление уходит при
оформлении, при ЮKassa — одно, после подтверждённой оплаты, без дублей;
текст сообщения; сбой сети; настройки в админке; константы `wp-config.php`.
Настоящий платёж и callback ЮKassa проверяются только с тестовыми ключами
заказчика (`docs/launch-checklist.md`, раздел 6).

Отдельно: `.pilot-baseline/` в корне стенда — материалы отката и сверки пилота
миграции контента (в git не попадают, удалять до приёмки нельзя). Свой
`render.php` там оставлен намеренно, чтобы отпечатки пилота снимались тем же
кодом, которым снимался baseline.
