# Whoopstore — постоянные правила разработки

## 1. Общий принцип

Это не новый магазин и не редизайн с нуля.

Задача проекта — реализовать утверждённые desktop/mobile макеты Figma на WordPress + WooCommerce, сохранив существующий контент, URL, товары, SEO, аналитику и коммерческую логику production-магазина.

Production является источником истины для существующих данных и бизнес-логики.

Текущий staging может быть только техническим фундаментом и не должен рассматриваться как полная модель production-магазина.

## 2. Production

* Никогда не изменять production без моего явного разрешения.
* Не менять DNS.
* Не выполнять destructive-операции на production.
* Не проводить реальные платежи.
* Не использовать реальные production API-ключи на staging.
* Если production недоступен, не делать вид, что его структура известна.
* Все предположения о production явно помечать как предположения.

## 3. Существующие данные

Нельзя без необходимости:

* пересоздавать существующие товары;
* менять product IDs;
* менять slugs/URLs;
* удалять товары;
* объединять существующие товары;
* менять существующую коммерческую логику;
* массово обновлять данные.

Ориентир — сохранить существующий магазин, а не построить его заново.

## 4. WooCommerce

Не создавать собственную модель товаров без необходимости.

Использовать стандартные WooCommerce products / variations там, где это соответствует модели магазина.

Важно:

**«устройство + конкретный тариф + срок» — отдельный WooCommerce product, а НЕ variation.**

Не объединять такие комплекты в variations только ради упрощения реализации.

Variations использовать только там, где вариант действительно является вариантом одного товара, например цвет/размер ремешка, если это соответствует существующей коммерческой модели.

## 5. Figma

Figma является источником истины для визуальной части проекта.

Не добавлять самостоятельно:

* новые страницы;
* новые UI-компоненты;
* новые пользовательские сценарии;
* новые тексты;
* новые функции;
* новые механики магазина,

если этого нет в Figma, ТЗ или существующей коммерческой логике.

Desktop и mobile рассматривать как полноценные композиции, а не просто как desktop, уменьшенный до мобильной ширины.

## 6. Архитектура

Не выбирать архитектурные решения только потому, что они проще для текущей задачи.

Перед крупными архитектурными изменениями необходимо учитывать:

* поддерживаемость;
* WooCommerce compatibility;
* соответствие Figma;
* существующую структуру production;
* возможность дальнейшей поддержки человеком;
* безопасность изменений;
* возможность отката.

Если production-контекст ещё неизвестен, сначала обозначить неизвестность, а не придумывать решение.

## 7. WordPress / WooCommerce

Предпочитать стандартные механизмы WordPress и WooCommerce, если они позволяют корректно реализовать требования.

Не заменять стандартную функциональность собственной реализацией без причины.

Любые overrides, hooks, filters, custom blocks и custom PHP должны иметь понятную архитектурную причину.

## 8. Изменения

Перед началом реализации сложной задачи:

1. Изучить существующую структуру.
2. Определить затрагиваемые файлы/механизмы.
3. Объяснить план изменений.
4. Проверить риски.
5. Только после этого вносить изменения.

Если я явно сказал «только анализ» или «ничего не изменяй» — никаких изменений не выполнять.

## 9. Git

В Git не добавлять:

* WordPress core;
* uploads;
* vendor plugins;
* database dumps;
* secrets;
* API keys;
* credentials;
* другие runtime/generated files.

В Git должны попадать только необходимые custom-разработки проекта.

## 9.1. Git commits

Сообщения коммитов должны быть на английском языке.

Используй Conventional Commits:
* `feat:` — новая функциональность;
* `fix:` — исправление ошибки;
* `refactor:` — изменение структуры кода без изменения поведения;
* `docs:` — изменения документации;
* `test:` — добавление или изменение тестов;
* `chore:` — технические изменения, конфигурация, зависимости и обслуживание проекта;
* `build:` — изменения, связанные со сборкой;
* `ci:` — изменения CI/CD;
* `perf:` — улучшения производительности;
* `style:` — изменения форматирования и стиля кода без изменения логики.

Выбирай тип коммита в соответствии с фактическим характером изменений.

Сообщение коммита должно быть кратким и описывать, что именно было изменено.

Используй повелительную форму, например: `fix: validate order access`.

Не используй русский язык, лишние пояснения, номера задач или ticket ID, если они явно не требуются проектом.

Перед коммитом проверь изменения и убедись, что в него попадают только относящиеся к задаче изменения.

Не объединяй в один коммит независимые логические изменения без необходимости.

Не создавай коммит только ради промежуточного состояния, если это не требуется текущим workflow.

При обычном завершении задачи, если изменения готовы и проверки пройдены, создай соответствующий коммит.


## 10. Staging

Staging используется для разработки и проверки.

Не считать staging идентичным production.

Не выполнять реальные коммерческие операции.

Не использовать реальные секреты интеграций.

## 11. Интеграции

Для YooMoney, СДЭК, Telegram и других внешних сервисов:

* не использовать реальные production credentials на staging;
* не проводить реальные списания;
* не ломать существующий production flow;
* перед изменением интеграции сначала изучить существующую реализацию.

## 12. QA

После реализации проверять не только внешний вид.

Минимально проверять:

* desktop;
* mobile;
* основные пользовательские сценарии;
* WooCommerce cart;
* checkout;
* account;
* product pages;
* URL;
* консоль браузера;
* broken assets;
* регрессии существующей функциональности.

## 13. Работа с AI

AI является исполнителем технической работы, но архитектурные решения должны быть объяснимы.

Не считать результат AI автоматически правильным.

Если есть несколько архитектурных вариантов:

* перечислить варианты;
* сравнить их;
* выбрать один;
* объяснить почему.

Не начинать реализацию, если я явно запросил только анализ.

## 14. Вёрстка

- Если два или более элемента имеют одинаковую визуальную роль и стили (например, кнопки, карточки, бейджи), использовать общий переиспользуемый класс/компонент вместо дублирования CSS.
- Повторяющиеся элементы должны иметь единый источник стилей, чтобы изменение общего стиля автоматически применялось ко всем экземплярам.
- Не создавать отдельные классы для каждого экземпляра одинакового элемента без необходимости.
- Если элементы похожи, но отличаются по назначению, состояниям или дизайну, не объединять их искусственно.
- Повторяющиеся секции и компоненты должны быть реализованы переиспользуемо, если это соответствует структуре и дизайну проекта.
- Все страницы и секции должны придерживаться единой визуальной системы: одинаковые элементы должны выглядеть одинаково, если Figma не предусматривает различия.
- Перед созданием нового компонента/класса проверить, существует ли уже подходящий переиспользуемый компонент/класс.
- Не дублировать CSS без необходимости.
- Не использовать inline styles, если стиль может быть реализован через существующий CSS-класс.

## 15. Установка

Не устанавливать, удалять, обновлять или заменять WordPress/WooCommerce plugins без явного разрешения. Перед использованием нового plugin сначала объяснить необходимость и влияние на архитектуру.

## 16. Главный принцип

**Сначала понять существующую систему → принять архитектурное решение → согласовать его → реализовать → проверить.**

Не делать необратимые или масштабные изменения только ради того, чтобы быстрее получить визуальный результат.
