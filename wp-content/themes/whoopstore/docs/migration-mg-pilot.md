# Пилот: контент страницы «Ремешки MG» в `post_content` (2026-09-16)

Первый шаг перевода сайта на архитектуру, где контент страниц заказчик правит
штатно через «Страницы», а данные магазина остаются динамическими из
WooCommerce. Пилот делается **только на странице MG (ID 94)**; по его итогам
решается, переносить ли тем же способом остальные страницы.

Причина миграции: сейчас весь контент лежит в PHP-паттернах темы, страницы в
базе пустые, а шаблоны не содержат `post-content` — правка страницы в админке
не даёт никакого результата. Разбор и общий план — в истории задачи.

## Границы пилота

Что входит:

* хлебные крошки и H1 страницы MG — в `post_content`;
* каталог из 6 разделов — динамический блок, читающий категории WooCommerce.

Что **не** входит и в этом заходе не трогается:

* FAQ, контакты и Телеграм — общие для четырёх страниц, остаются паттернами в
  шаблоне; мигрируют отдельной задачей сразу для всех страниц;
* `audience-marquee` и `subscriptions-compare`;
* Главная, «Ремешки 5.0», «Подписки»;
* header, footer, меню;
* WooCommerce: товары, цены, корзина, оформление заказа, страница товара;
* `assets/css/theme.css` — правится только если сверка покажет расхождение, и
  тогда отдельным коммитом, чтобы правку вёрстки было видно отдельно от
  миграции;
* паттерны `page-head-straps-mg.php` и `straps-mg-catalog.php` — остаются в
  репозитории до отдельной команды заказчика после приёмки: пока они на месте,
  откат не требует восстановления файлов.

## Точка отката

| Что | Где |
|---|---|
| Ветка пилота | `pilot/straps-mg-content` |
| Исходный коммит | тег `pilot-mg-baseline` → `400bace` |
| Дамп БД до изменений | `.pilot-baseline/db/whoopstore-before-pilot.sql` (2,3 МБ) |
| HTML-дампы и отпечатки | `.pilot-baseline/html/*.before.*` |
| Ревизии страницы 94 | включены, `WP_POST_REVISIONS = 10` |

`.pilot-baseline/` лежит в корне стенда и **не попадает в git**: корневое
правило `/*` в `.gitignore` игнорирует всё неразрешённое, дамп БД дополнительно
закрыт правилом `*.sql`.

Быстрый откат — один файл:

```bash
git checkout -- wp-content/themes/whoopstore/templates/page-straps-mg.html
```

Шаблон снова рендерит паттерны, контент страницы просто перестаёт
использоваться и никуда не пропадает.

Полный откат:

```bash
git checkout pilot-mg-baseline -- wp-content/themes/whoopstore
php8.2 /usr/local/bin/wp-cli.phar db import .pilot-baseline/db/whoopstore-before-pilot.sql
```

## Инструменты сверки

Стенд закрыт HTTP Basic Auth на уровне Caddy, поэтому страницы рендерятся
локально (системный `php` — 5.6, WordPress на нём не поднимется):

```bash
/usr/local/php/cgi/7.4/bin/php .pilot-baseline/render.php /remeshki-whoop-mg/ \
  > .pilot-baseline/html/mg.after.html

python3 .pilot-baseline/fingerprint.py .pilot-baseline/html/mg.after.html \
  > .pilot-baseline/html/mg.after.fp.txt

diff .pilot-baseline/html/mg.before.fp.txt .pilot-baseline/html/mg.after.fp.txt
```

Рендер воспроизводим: два прогона подряд дали побайтово одинаковый файл, поэтому
sha256 в отпечатке — надёжный признак «ничего не изменилось».

`fingerprint.py` показывает то, что обязано совпасть: размер, хеш, атрибуты
`<main>`, список его прямых потомков, счётчики ключевых классов, заголовки
разделов каталога и все цены на странице.

## Чек-лист приёмки

1. `diff` отпечатков MG до/после: ожидаемая дельта — только классы `<main>` и
   новый `div.entry-content`.
2. Прямые потомки `<main>` те же и в том же порядке.
3. Заголовки шести разделов и все 24 цены совпадают.
4. `post_content` страницы 94 не содержит `device-card`, `catalog-section`, `₽`.
5. **Сохранить страницу в редакторе без единой правки → повторить проверку 4.**
   Ключевой тест: именно здесь старая архитектура заморозила бы каталог.
6. После сохранения в редакторе в БД не появилось записей `wp_template` /
   `wp_template_part`.
7. Изменить цену товара MG в «Товарах» → цена меняется на странице без правки
   самой страницы; вернуть цену обратно.
8. Изменить H1 в редакторе → изменение видно на сайте.
9. Отпечатки Главной, «Ремешков 5.0» и «Подписок» совпадают с baseline.
10. Скриншоты desktop и mobile против текущих.
11. Консоль браузера без ошибок, битых ассетов нет.
12. Якоря, внутренние ссылки, добавление товара в корзину со страницы MG.

## Результаты пилота (шаги 2–4, 2026-09-16)

Выполнено на ветке `pilot/straps-mg-content`:

* `whoopstore_breadcrumbs()` вынесена из `whoopstore_page_head()` — вывод трёх
  страниц совпал с baseline побайтово;
* заведены два динамических блока, `whoopstore/breadcrumbs` и
  `whoopstore/category-catalog` (`inc/blocks.php`, `inc/blocks/*`);
* `templates/page-straps-mg.html` переведён на `post-content`;
* `post_content` страницы 94 — 669 байт: группа `page-head` с крошками и H1
  плюс тег блока каталога с шестью slug'ами.

Ключевые цифры сверки MG: `device-card` 180 → 180, разделов 6 → 6, цен 24 → 24
(набор тот же), порядок секций не изменился, `<main>` на странице один.
Страницы 5.0, «Подписки» и Главная совпадают с baseline побайтово.

Проверка на заморозку пройдена: сохранение страницы через тот же REST-маршрут,
которым пользуется редактор, оставило `post_content` неизменным (669 байт),
записей `wp_template` / `wp_template_part` в базе не появилось, а
отрендеренная страница совпала побайтово с состоянием до сохранения. Смена
цены товара 198 на тестовое значение сразу отразилась на странице без её
редактирования; исходная цена возвращена.

Ожидаемые и объяснённые отличия DOM: класс `catalog-page` переехал с `<main>`
на холст `post-content`, появился `div.entry-content`, `.page-head` стала
блочной группой с `is-layout-flow`, H1 получил `wp-block-heading`, у двух
иконок крошек добавился `decoding="async"` (содержимое `post-content` проходит
через `wp_filter_content_tags()`), плюс краевой пробельный шум: WooCommerce в
фильтре `render_block` делает `trim()` вывода **любого** блока сайта, ещё до
проверки, свой ли это блок — см. `BlockTypesController::add_data_attributes`.

Проверено, что конфликт специфичности не сработал: правило ядра
`:root :where(.is-layout-flow) > * {margin-block-start:24px}` имеет
специфичность (0,1,0), а `.page-head > .page-head__title {margin:30px 0 0}` —
(0,2,0), поэтому отступ H1 остался прежним.

Сверх плана понадобилось одно изменение: атрибуту `label` блока крошек
добавлена `"role": "content"`. Внутри `templateLock: "contentOnly"` ядро
оставляет редактируемыми только блоки, у которых есть атрибут с ролью
`content`; без этого крошки внутри заблокированной группы стали бы
нередактируемыми. На фронт не влияет.

## Статус приёмки: пилот визуально НЕ принят

**Не выполнено:** проверка в браузере — открыть страницу 94 в Gutenberg,
нажать «Обновить», убедиться, что поля внутри `contentOnly` редактируются, и
сверить desktop/mobile глазами.

**Причина:** staging нестабильно доступен в браузере (сайт закрыт HTTP Basic
Auth на уровне Caddy, учётных данных у исполнителя нет), поэтому пункты 5, 8,
10 и 11 чек-листа приёмки остаются открытыми. Серверная половина этих проверок
пройдена и описана выше, клиентская — нет: как именно JS редактора сериализует
блоки при нажатии «Обновить», headless воспроизвести нельзя.

**Следствия, действующие до визуальной приёмки:**

* пилот считается технически выполненным, но **не принятым**;
* паттерны `page-head-straps-mg.php` и `straps-mg-catalog.php` **не удаляются**
  и остаются точкой мгновенного отката;
* остальные страницы (5.0, «Подписки», Главная) **не мигрируются**;
* общие секции (FAQ, контакты, Телеграм) **не мигрируются**.

Отдельно: страница 93 («Ремешки для WHOOP 5.0») в админке выглядит пустой —
это ожидаемо, она не мигрирована, её контент по-прежнему в паттернах темы.
Пустое автосохранение у неё (ревизия `93-autosave-v1`) создаётся самим
редактором при открытии и ни на что не влияет.
