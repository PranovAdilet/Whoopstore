## Этап 6: общие секции → синхронизированные паттерны

Продолжение миграции контента в редактируемый вид. Пилот MG показал, как
переносить контент конкретной страницы; здесь решается другая задача — три
секции, которые стоят **сразу на четырёх страницах** и сейчас правятся только
в коде.

Секции: FAQ, контакты, Телеграм. Страницы: Главная, «Ремешки 5.0»,
«Ремешки MG», «Подписки».

## Механизм и почему он такой

В шаблонах ссылка на паттерн темы заменяется ссылкой на синхронизированный
паттерн в базе:

```diff
-<!-- wp:pattern {"slug":"whoopstore/telegram-subscribe"} /-->
+<!-- wp:block {"ref":269} /-->
```

Что это даёт:

* **один источник на четыре страницы.** Правка в «Внешний вид → Редактор →
  Паттерны» меняет все четыре страницы разом — ровно так же, как сейчас это
  делает правка PHP. Копии в контенте четырёх страниц неизбежно разъехались бы;
* **не тянет за собой миграцию остальных страниц.** Главная, 5.0 и «Подписки»
  продолжают жить на паттернах темы; их контент этот этап не трогает;
* **нечего замораживать** — в этих секциях нет данных WooCommerce.

`patterns/telegram-subscribe.php` **оставлен на месте** и больше не
используется — точка мгновенного отката.

### Контейнеры

По согласованному варианту A сырые `<div>` переведены в блоки с сохранением
классов: `.telegram-subscribe__content` стал `wp:group`.

`.telegram-subscribe__media` осознанно оставлен блоком `wp:html`: это
декоративный мокап телефона с `aria-hidden`, которого `wp:group` не несёт, а
перевод картинки в `core/image` добавил бы обёртку `<figure>` и перенёс бы
класс с `<img>` на неё.

### Почему понадобилась правка CSS

Не косметика, а необходимость. `.telegram-subscribe` — flex-контейнер. Став
блоком-группой, она получила от Gutenberg `is-layout-constrained`, а у ядра
есть правило:

```css
.is-layout-constrained > :where(:not(.alignleft):not(.alignright):not(.alignfull)) {
	max-width: var(--wp--style--global--content-size);
	margin-left: auto !important;
	margin-right: auto !important;
}
```

`margin-inline: auto` на flex-элементах съедает свободное место — текст и
телефон разъехались бы по краям вместо 84px между ними. Лечение:

1. у группы `.telegram-subscribe` снят `layout: constrained` — раскладку
   секции задаёт наш flex, а не контейнер WP;
2. одна строка гасит block-gap ядра на колонках, иначе телефон съезжал вниз
   на 24px относительно текста.

Селектор `.telegram-subscribe > *` имеет специфичность (0,2,0) против (0,1,0)
у правила ядра, то есть выигрывает надёжно, а не по порядку подключения.

### Результат сверки

Структура секции: **11 элементов было, 11 стало**, порядок и вложенность те же,
`aria-hidden` и `<span>` с ограничением ширины заголовка на месте. Отличия
только в двух списках классов:

```
.telegram-subscribe          + is-layout-flow wp-block-group-is-layout-flow
.telegram-subscribe__content + wp-block-group is-layout-flow …
                             − has-global-padding is-layout-constrained …
```

Потеря `is-layout-constrained` у `__content` ни на что не влияет: его детям она
давала `max-width: 1120px` и `margin-inline: auto`, что в колонке 420px ничего
не меняло, а block-gap во flow-варианте точно такой же.

Вне секции на страницах изменились только `?ver=` у `theme.css` и убранный
HTML-комментарий из старого паттерна: каждая из четырёх страниц стала легче
ровно на 219 байт.

Проверки: паттерн разбирается в 8 блоков без единого freeform,
`serialize_blocks` возвращает исходник байт в байт, `wp_template` /
`wp_template_part` — 0 записей, `post_content` страницы 94 не тронут, editor
smoke 21 из 21. Визуально принято заказчиком на Главной.

### Контейнеры

В блоки переведены `.contact-block__info` и `.contact-block__messengers-wrapper`.

В `wp:html` осознанно оставлены два узла:

* **карта.** `core/image` рендерит `<figure class="wp-block-image">` с `<img>`
  внутри, и класс `contact-block__map` сел бы на `<figure>`. Тогда
  `flex: 1 1 50%`, `height: 370px` и `object-fit: cover` перестают
  применяться — геометрия секции разваливается. Плата: карту нельзя заменить
  через медиатеку, только правкой HTML-блока. Реальной карты там и нет, это
  статичный скриншот по макету;
* **иконки мессенджеров.** На обёртке `aria-hidden="true"`, которого `wp:group`
  не несёт, а сами иконки декоративные.

### Пути иконок

`get_theme_file_uri()` заменён на root-relative пути:

```
/wp-content/themes/whoopstore/assets/icons/max-logo.svg
/wp-content/themes/whoopstore/assets/icons/telegram-logo.svg
```

Не абсолютные: контент не привязывается к домену и одинаково работает на
`whoop.1c2.ru`, через SSH-туннель на `localhost:8094` и на будущем проде. Та же
конвенция, что уже принята в теме для картинок из `uploads`. Плата: контент в
базе ссылается на имя папки темы — при переименовании темы иконки отвалятся.

### Почему понадобилась правка CSS

`.contact-block` (`display:flex; align-items:stretch`) и
`.contact-block__messengers-wrapper` (`display:flex; justify-content:space-between`)
стали блоками-группами и **впервые** получили `is-layout-flow`. Правило ядра
`:root :where(.is-layout-flow) > * {margin-block-start:24px}` тогда сдвинуло бы
инфо-карточку на 24px относительно карты (ломая `align-items:stretch`) и иконки
мессенджеров относительно юр. строки.

```css
.contact-block > .contact-block__info,
.contact-block__messengers-wrapper > .contact-block__messengers {
	margin-block-start: 0;
}
```

Правило **адресное, а не `> *`**: у `p.contact-block__legal` есть собственный
`margin-top: auto` со специфичностью (0,1,1), которым юр. строка прижата к низу
карточки, и общее правило (0,2,0) его бы перебило. Проверено до реализации.

Где именно осядут классы, выяснено заранее прогоном кандидатной разметки через
`do_blocks()` — без правки файлов. Предсказание совпало с результатом.

Проверки: 9 блоков без freeform, `serialize_blocks` = исходник байт в байт,

### Канонический вид блочных комментариев

Первая версия паттерна не проходила `serialize_blocks == исходник`: в классах
секции есть двойные дефисы (`card--light`, `section-subtext--light`), а
WordPress внутри блочных комментариев кодирует их как `\u002d\u002d` —
последовательность `--` внутри HTML-комментария недопустима по стандарту.

Рукописная разметка с литеральными `--` парсером принимается, но при первом
сохранении из редактора WordPress переписал бы весь паттерн в канонический вид.
Поэтому в базу сразу записан канонический результат `serialize_blocks()`, и
сохранение без правок — холостая операция.

В 6.1 это не всплыло только потому, что в классах Телеграма двойных дефисов нет.
**Для FAQ в 6.3 учитывать заранее.**

По решению заказчика старые селекторы (`.faq__question`, `.faq__chevron`,

на `<summary>` есть, у новой его нет вовсе, поэтому при откате вторая иконка не
появляется. Дубли уйдут вместе с удалением старых паттернов.

### Иконка

`<summary>` в `core/details` — это RichText, инлайновый SVG внутри не выживает.
Иконка переехала на `::after` с `mask` из того же файла
`assets/icons/faq-chevron.svg`, поэтому геометрия «плюса» та же по построению.
Поворот на 45° при раскрытии сохранён.

### Мобильная ширина текста вопроса

Раньше её держал `<span class="faq__question-text">` с `max-width: 224px`.
В `summary` этого span больше нет — текст стал анонимным элементом и напрямую
не таргетируется. Ограничение выражено колонкой грида
`grid-template-columns: minmax(0, 224px) 1fr`, иконка прижата `justify-self: end`.

### Найденный и исправленный баг: ответ прилипал к низу карточки

Проявился после приёмки структуры, при раскрытии вопроса. Причина —
**специфичность, а не отсутствие padding**:

```css
:root :where(.is-layout-flow) > :last-child { margin-block-end: 0; }  /* (0,2,0) */
.faq__answer { margin: 0 30px 22px; }                                 /* (0,1,0) */
```

`core/details` — layout-контейнер, абзац ответа в нём последний ребёнок, и
правило ядра обнуляло 22px снизу. `:where()` специфичности не добавляет, а
`:root` и `:last-child` дают по (0,1,0) каждый. В старой разметке бага не было:
у `<details>` не было класса раскладки.

Исправление — одно правило со специфичностью (0,3,0), то есть выигрывающее по
специфичности, а не по порядку подключения файлов:

```css
.faq__list > .faq__item > .faq__answer { margin-block-end: 22px; }
```

Значение то же, что в `.faq__answer`; старой разметке правило не мешает.

## Что важно помнить дальше

**`ref` — это ID записи в базе.** Если база будет пересоздана (а прод —
отдельный сайт), ID изменится, и шаблон молча отрендерит пустоту: `core/block`
при отсутствии записи возвращает пустую строку, без ошибки. При переносе на
прод синхронизированные паттерны нужно переносить вместе с их ID либо
править `ref` в шаблонах.

**Текст уезжает из кода в базу.** После этапа тексты этих секций наши деплои
темы больше не несут. Это и есть цель, но при переносе контента это отдельная
сущность, о которой легко забыть.

**`<span>` в заголовке Телеграма.** На нём держится перенос заголовка на две
строки по макету. Это не формат Gutenberg, а произвольный `<span>`, и редактор
может выбросить его при первой правке заголовка. По решению заказчика от
2026-09-17 пока оставлено как есть. Чинится переносом `max-width: 323px` со
`span` на сам `.telegram-subscribe__title` — раньше мешало автоцентрирование
ядром, но после снятия `layout: constrained` это ограничение отпало.

## Динамические блоки темы

`inc/blocks/`: `breadcrumbs`, `category-catalog`, `product-grid` (плюс
`search-results` из другой задачи). Все серверные: в контенте лежат только
настройки, разметка собирается при каждом запросе, поэтому карточки товаров
не могут «застыть» в базе.

## Что осознанно осталось в коде

Этап редактируемости закрыт 2026-09-18 (коммит `ff22057`, тег
`editor-stage-done`). Дальше в Gutenberg ничего не переносится без отдельного
решения. Ниже — почему оставшееся живёт в коде. Это не недоделка: у каждой
позиции перенос либо ломает работающую механику, либо замораживает живые
данные, либо не даёт заказчику реального удобства.

### Причины

1. **Секции с залипанием и каруселью завязаны на DOM-структуру и JS.**
   Слайды «Преимуществ» (`advantages-sticky-scroll.js`) и лента
   «Персонализируйте» (`straps-carousel.js`) обращаются к разметке напрямую
   по классам и порядку элементов, высота залипания считается из числа
   слайдов в PHP. Любая правка структуры в редакторе — удалённый или
   переставленный блок — ломает механику, а проверить её можно только в
   браузере. Перенос потребовал бы собственного блока с зафиксированной
   структурой, это отдельная задача.
2. **Бегущая строка: список дублируется ради бесшовной анимации.**
   `audience-marquee.php` печатает список аудиторий дважды, иначе на стыке
   виден разрыв. В паттерне заказчику пришлось бы править каждый пункт в двух
   местах и следить, чтобы копии совпадали. Вынос требует отдельной логики
   клонирования (второй экземпляр строит скрипт), то есть нового JS.
3. **Таблица сравнения: у desktop и mobile разные представления.**
   `subscriptions-compare.php` собирает из одного массива данных и таблицу для
   desktop, и карточки для mobile. В контенте это две копии каждой строки.
   Редактируемой её делает только собственный блок с полями или переделка
   мобильной вёрстки. Следствие, о котором стоит знать: опечатка
   «эпотребительного» (перенесена из макета дословно) исправляется только в
   коде.
4. **Динамические товарные секции получают данные из WooCommerce.**
   Сетка устройств, «Аксессуары», «Активация и продление», каталоги, тарифы
   собираются из товаров при каждом запросе. Синхронизированный паттерн —
   статичный HTML: он заморозил бы названия, цены и ссылки. Поэтому товарные
   секции — это либо PHP-паттерны темы, либо динамические блоки
   (`category-catalog`, `product-grid`), в которых хранятся только настройки.
   Заголовки «Аксессуары» и «Активация и продление» остаются в коде вместе
   со своими секциями (у «Активации» к тому же свой CSS-контракт, см.
   таблицу ниже).
5. **Изображения в существующей HTML/`<picture>`-разметке.**
   Все 25 картинок в паттернах лежат в блоках `wp:html`. Штатный блок
   «Изображение» оборачивает `<img>` в `<figure>` — селекторы вида
   `.advantages__stat-media img` перестают совпадать; `<picture>` с отдельной
   мобильной картинкой (FAQ, промо ремешков) он не умеет вовсе. Заменить
   картинку можно правкой пути в HTML-блоке, но не через медиатеку.
6. **Ссылки App Store и Google Play ждут реальных адресов.**
   Кнопки «Скачать» ×2 и «Подключить» в «Приложениях» (`wp_block` 280) —
   сырые `<a href="#">` в HTML-блоках: блок «Кнопка» добавил бы две обёртки и
   сломал сетку карточек (коммит `63c2427`). Адреса вписываются в HTML один
   раз, когда их пришлёт заказчик. Иконки мессенджеров в контактах пока без
   ссылок по той же причине — нет адресов.

Два правила работы в редакторе, которые должны попасть в инструкцию для
заказчика:

* **Перед правкой паттерна перезагрузить вкладку редактора.** Открытая
  вкладка держит разметку на момент открытия и при сохранении перезаписывает
  более свежую версию целиком, без предупреждения — так 2026-09-18 в
  `wp_block` 269 вернулся уже удалённый `<span>`.
* **Сохранение шапки или подвала создаёт их копию в базе** (`wp_template_part`),
  которая перекрывает файл темы. Последующие правки `parts/header.html` /
  `parts/footer.html` на сайте не появятся, пока копию не сбросить
  («Сбросить» в меню части шаблона). На 2026-09-18 таких копий 0.

## Что редактируется через WooCommerce

Названия, цены, старые цены, бейджи, фотографии, состав и порядок карточек во

секции, потому что те же три товара выводятся ещё и на Главной с другим
порядком по макету (подробности — в шапке `inc/blocks/product-grid/render.php`).

## Перенос на production: главное ограничение

**Синхронизированные паттерны — это записи в базе, а не файлы темы.** Деплой
файлов их не переносит. При переезде на production нужно:

1. перенести содержимое всех 14 записей `wp_block`;
2. проследить, чтобы их ID совпали с `ref` в шаблонах, либо поправить `ref`
   в четырёх файлах шаблонов под новые ID.

Если ID разойдутся, шаблон **молча отрендерит пустоту**: `core/block` при
отсутствии записи возвращает пустую строку, без ошибки и без записи в лог.
То же касается `post_content` страниц 93 и 94.

## Главная и `show_on_front`

Главная по-прежнему **не является страницей**: `show_on_front = posts`,
`page_on_front = 0`, блока `post-content` в `front-page.html` нет. Поэтому её
секции живут в синхронизированных паттернах, а не в `post_content`. Это
осознанное ограничение текущего этапа: перевод Главной в статическую страницу
меняет настройку сайта и требует отдельной приёмки.

## Незакрытые долги

1. **`<span>` в заголовке `straps-promo`** — держит приглушённый цвет второй
   строки «(более 50 цветов)». Это не формат Gutenberg, и редактор выбросит его
   при первой правке заголовка. Штатная замена (формат «цвет текста») рендерит
   `<mark>` с инлайновым стилем, то есть меняет один нестандартный элемент на
   другой. Нужно решение по макету.
2. **Две категории без плитки** на «Ремешках 5.0» — `cloudknit-5-0` и
   `superknit-luxe-5-0`. Следствие того, что в макете шесть плиток на семь
   разделов и две плитки называются одинаково. Подробности — в
   `figma-straps-50-notes.md`.
3. **18 неиспользуемых PHP-паттернов** в `patterns/` — оставлены как точки
   отката, ждут отдельной команды на удаление. Используются только семь:
   `device-grid`, `accessories-grid`, `activation-grid`, `audience-marquee`,
   `advantages-sticky-scroll`, `straps-personalize`, `subscriptions-compare`.
4. **Дублирующие правила CSS** — для FAQ, Телеграма и `no-display` старые
   селекторы (под разметку со `<span>` и с инлайновым SVG) сохранены рядом с
   новыми, чтобы откат оставался однокомандным. Уйдут вместе с удалением
   старых паттернов.
   Туда же относится `.advantages__stats-title span` — после переноса
   «15 показателей» (`wp_block` 299) `<span>` в заголовке нет, правило
   ничего не находит.
5. **Инструкция для заказчика не написана.** Должна содержать, где что
   правится (Главная и «Подписки» — только через Паттерны, не через
   Страницы; страница «Подписки Whoop» в Страницах пустая, и вписанное туда
   на сайте не появится), что FAQ, Контакты и Телеграм — общие для четырёх
   страниц, не трогать `wp:html`, и оба правила из раздела «Что заказчик
   редактирует через Gutenberg».

# «15 показателей здоровья» → синхронизированный паттерн (2026-09-18)

Нижняя половина секции «Преимущества» — заголовок «Более 15 ключевых
показателей…», 15 карточек и кнопка «Посмотреть ещё» — вынесена из
`patterns/advantages-sticky-scroll.php` в `wp_block` **299** «Главная — 15
показателей здоровья». В шаблоне Главной он стоит сразу после паттерна
преимуществ. Верхняя половина (слайды с залипанием) осталась в PHP: её
скрипт работает только внутри `.advantages__scroll` и нижнюю часть не
трогал, высота «дорожки» задаётся её собственной `--advantages-count`.

Структура: корень `group.advantages-stats` → `heading` h3 → сетка
`group.advantages__stats` из 8 карточек → `group#advantages-more.advantages__more`
(4 карточки, `heading` h4 «Дополнительно в WHOOP MG:», 3 карточки) → кнопка.
Карточка — `group.advantages__stat.card`: слот картинки в `wp:html` (байт в
байт из прежней разметки: `core/image` обернул бы `<img>` в `<figure>`) и
`group.advantages__stat-body` с двумя абзацами. Сборка —
`.pilot-baseline/db/build-advantages-stats.php`, данные берутся из прежнего
паттерна, руками ничего не перепечатано.

Что потребовалось вне паттерна:

* **CSS** — блок «Правка 2026-09-18» в `theme.css` перед правилом VO₂ Max:
  отступ секции перенесён на корень, ширина заголовка — на `<h3>` вместо
  `<span>`, погашены отступы flow-раскладки ядра в сетке и карточке,
