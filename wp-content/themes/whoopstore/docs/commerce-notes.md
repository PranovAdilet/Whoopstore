# Коммерческая часть на staging (2026-09-15)

Решение заказчика: перенос production не обязателен, коммерческую часть
настраиваем на текущем staging. Production не трогаем и данных оттуда не берём.
Всё, чего нет в Figma или у заказчика, не выдумано — это блокеры внизу.

## Что работает

Сценарий **товар → корзина → оформление → заказ** проходит на настоящем
WooCommerce (проверено через Store API — те же маршруты, что вызывает форма):

* 61 товар в каталогах, на Главной и на «Подписках»; кнопки «Купить» ведут на
  страницы товаров;
* корзина (шапка, степпер, drawer) — как и раньше, Store API;
* форма «Ваш заказ» создаёт заказ WooCommerce: доставка «Экспресс доставка» и
  «Самовывоз», тестовая оплата, поля Telegram / согласие / комментарий;
* заказ из одних виртуальных товаров (подписки, активация) — без доставки и адреса;
* уведомление о заказе в Telegram собирается; пока нет бота, текст пишется в журнал.

## Оформление заказа

Форма → `POST /wc/store/v1/checkout`. Соответствие полей:

| Поле формы | В заказе WooCommerce |
|---|---|
| ФИО | billing first_name (фамилия не обязательна) |
| Телефон (+7 и 10 цифр) | billing phone `+7XXXXXXXXXX` |
| E-mail | billing email |
| Telegram | дополнительное поле заказа `whoopstore/telegram` |
| Город / Индекс / Улица + Дом / Квартира | shipping (и billing) city / postcode / address_1 / address_2 |
| Комментарий к заказу | заметка покупателя (customer_note) |
| Согласие с политикой | дополнительное поле `whoopstore/privacy-consent` |

Серверные проверки (ответ 400 с текстом, заказ не создаётся): нет согласия;
телефон короче 11 цифр (штатная настройка «телефон обязателен» Store API не
применяет); нет города / индекса / улицы при доставке по адресу. Адрес не нужен
при самовывозе и в заказе из одних виртуальных товаров — форма прячет эти поля.

После оформления: способ оплаты с переходом на платёжную страницу (ЮKassa)
уводит туда; оплата без перехода показывает модалку «Заказ оформлен» с настоящим
номером заказа. После успешной оплаты в ЮKassa покупатель возвращается на
Главную с той же модалкой (номер — только при совпавшем ключе заказа), см.
`docs/launch-checklist.md`, раздел 6.

**Отступления от макета:** строка ошибки над кнопкой и неактивная кнопка на
время отправки (состояния ошибки в Figma нет); строка «Срок доставки» скрыта,
пока у тарифа нет срока; плиток доставки столько, сколько настроено способов.

## Telegram

Токен бота и ID чата заказчик вводит сам: WooCommerce → Настройки →
Дополнительно → Telegram. Там же поиск чата и тестовое сообщение
(2026-09-18, `whoopstore-commerce/telegram-admin.php`). Значения хранятся в
опциях, в git их нет. Константы в `wp-config.php` важнее настроек:

```php
define( 'WHOOPSTORE_TELEGRAM_BOT_TOKEN', '…' );
define( 'WHOOPSTORE_TELEGRAM_CHAT_ID', '…' );
```

Сообщения не с боевого окружения помечаются `[staging]`. Пока токена и чата
нет, сообщение не отправляется, текст — в журнале WooCommerce (источник
`whoopstore-telegram`), в заказе — заметка. `api.telegram.org` с
хостинга доступен. Уведомление уходит в момент оформления; при оплате через
ЮKassa — только после подтверждённой оплаты (2026-09-18).

## Локализация (2026-09-16)

Русского пакета WooCommerce на стенде не было вовсе — отсюда весь английский.
Установлен штатной командой: `wp language plugin install woocommerce ru_RU`
(276 файлов, включая JSON для скриптов блоков — они подключаются через
`wp_set_script_translations`). Переводы лежат в `wp-content/languages/` и **в git
не попадают**: при переносе на другой сервер команду нужно повторить.

Проверено после установки: статусы заказов, ошибки Store API («Предоставленный
Email недействителен»), цена со скидкой, интерфейс блоков корзины.

Что осталось нашим кодом:

* `%s has been added to your cart.` — этой строки в русском пакете нет; переведена
  фильтром `ngettext` в `inc/woocommerce/template-hooks.php`. Видна только в
  запасном пути без JS.
* Три статические надписи в содержимом страницы `/cart/` («Your cart is currently
  empty!», «New in store», «You may be interested in…») заменены на формулировки
  из того же русского пакета. Структура блоков не менялась: число блоков до и
  после — 24. На `/checkout/` английского текста в содержимом нет.
* Прежние фильтры «Распродажа» / «Выбрать опции» / «Выбрать вариант» оставлены:
  «Распродажа» — формулировка из макета (в пакете «Распродажа!»).

## Штатные `/cart/` и `/checkout/` — почему остаются блочными

Разбор 2026-09-16: заменять их на классические шорткоды **нельзя**.
Дополнительные поля заказа (Telegram, согласие с политикой) — механизм блоков и
Store API: в `CheckoutFieldsFrontend` есть хуки только кабинета, адресов и
просмотра заказа, на классической форме этих полей нет, а наша проверка согласия
висит на хуке Store API. Классический чекаут принимал бы заказы без согласия.

Из вёрстки на эти страницы нет ссылок (оформление идёт в панели корзины);
достижимы они вручную по адресу и по ссылке «Просмотр корзины» в уведомлении при
работе без JS. ТЗ требует сохранить штатные корзину и оформление — оставляем как
запасной путь, не редизайним и не удаляем.

## Оптимизация скриптов (не связана с 504)

На страницах без товарных форм (Главная, каталоги, «Подписки») WooCommerce ставил
jQuery, jQuery Migrate, blockUI, `wc-add-to-cart`, `js-cookie` и свой
frontend-скрипт. Зависимостей от них на этих страницах нет (проверено по
`wp_scripts`), наша корзина работает на Store API без jQuery. Сняты в
`inc/setup.php`; страницы WooCommerce, корзина, оформление и кабинет получают всё
в полном объёме. Сбор источника заказа (`sourcebuster-js`, `wc-order-attribution`)
не тронут — он нужен на всех страницах, включая точку входа.

Результат: Главная 14 → 8 скриптов, каталог 5.0 11 → 5, «Подписки» → 6. Страница
товара (22), `/cart/` (60) и `/shop/` (50) не изменились.

**Это обычная оптимизация, а не лечение 504** — причина тех отказов вне нашего
контура, см. следующий раздел.

## Инфраструктурный блокер: 504 на участке Caddy → Beget

Замеры 2026-09-16 (подробности — в отчёте сессии):

* наш сервер отдаёт 100 параллельных запросов к статике за 77 мс, все 200; 10
  параллельных PHP-страниц — в среднем 1,27 с; машина не перегружена;
* gzip включён, статика кэшируется на 7 дней;
* Caddy на 60 параллельных запросов отвечает за 0,2 с, но это его собственные
  401 — до нашего сервера они не доходят.

Отказы возникают на участке **Caddy (`2.26.87.109`) → Beget**. Ни конфигурацию
nginx/PHP/WordPress, ни объём страницы это не лечит. Чтобы измерить именно этот
участок, нужны: логин и пароль Basic Auth стенда (тогда ту же нагрузку можно
прогнать через прокси и сравнить) и доступ к настройкам и логам Caddy.

## Браузерная QA 2026-09-16 и исправления

Проверено в браузере (desktop 1440×900 и mobile 390×844). Работает: карточки и
переход на товар, плитки доставки с подписями из макета, скрытие полей адреса
при самовывозе, пересчёт сумм, оформление заказов (№240 ремешок/самовывоз,
№241 подписка, №242 повторный контрольный), отсутствие блока доставки у заказа
из одних виртуальных товаров, ответ 400 без согласия (ложной модалки нет).

Найдено и исправлено:

1. **Рассинхрон способа доставки.** Плитка переключалась, а поля адреса и суммы
   оставались от прошлого выбора (примерно каждый третий клик). Причина —
   интерфейс перерисовывался только по ответу Store API. Теперь плитка и поля
   адреса переключаются сразу, суммы показывают стоимость выбранной плитки, а
   ответ сервера их уточняет; ответы на устаревшие клики отбрасываются
   (`pendingRateId`, `rateRequestToken` в `assets/js/cart-drawer.js`).
2. **Невидимый оверлей после закрытия модалки.** `[hidden]` объявлен только в
   `theme.css`; когда тот не догрузился (504 на статике), у `.order-modal`
   оставался `display: flex` из `woocommerce.css`. Правило `[hidden]` повторено
   рядом с самими оверлеями в `woocommerce.css`.
3. **«Заказ оформлен» с пустым номером и без запроса к API** (дважды). Это
   поведение старой, макетной версии `cart-drawer.js` — значит, браузеру или
   тестовому прокси досталась устаревшая копия скрипта (в разметке `?ver=`
   верный, по времени файла). Защита: модалку показывает только код, получивший
   ответ оформления, — он ставит `data-order` с номером заказа, а CSS без этого
   атрибута её не показывает.

**Ретест 2026-09-16 после исправлений — пройден** (desktop и mobile, полный сброс
кэша): 6/6 быстрых переключений плитки на каждом вьюпорте дают согласованное
состояние полей адреса и сумм; после закрытия модалки `display: none`, клики по
странице проходят; ложная модалка не воспроизводится (`data-order` пуст до
оформления). Контрольные заказы №243–246, все с ответом 200.

Осталось (инфраструктура, не код): стенд отдаёт **504 на статику при
параллельной загрузке** — из-за этого не грузятся часть фото, `cart.js` и
скрипты штатных `/cart/` и `/checkout/`.

Отсюда же «счётчик корзины не обновляется без перезагрузки»: логика `cart.js`
проверена отдельно (прогон файла на заглушке DOM — после добавления счётчик
становится 1, кнопка корзины появляется, показываются степпер и тост, обычного
POST нет), а `cart.js` присутствует в списке файлов с 504 в отчёте QA. Без него
форма товара уходит обычным POST, и счётчик виден только после перезагрузки.
Вопрос к хостингу/Caddy. Заодно: страницы `/cart/` и `/checkout/` тянут ~60
скриптов WooCommerce Blocks и в нашем сценарии не используются (оформление идёт
в панели корзины) — можно ли их облегчить или закрыть, нужно решение.
